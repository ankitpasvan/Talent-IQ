01. Project Overview

Talent IQ is a full-stack, real-time technical interview and pair-programming platform designed to streamline remote developer assessments. It unites high-stakes video conferencing, multi-language code editing, algorithmic challenge suites, and isolated sandboxed execution into a single, cohesive browser environment.

The Problem It Solves

Technical interviewing in most organizations is fragmented across incompatible software:

  • Video Conferencing: Zoom, Google Meet, or Microsoft Teams.
  • Code Scratchpads: Google Docs, generic online editors, or CoderPad.
  • Compilation & Testing: Local terminals or third-party web compilers.

This workflow causes friction: candidates context-switch across 3–4 tabs, interviewers cannot verify compiler output deterministically, and candidate code is vulnerable to copy-paste leaks. Talent IQ solves this by embedding WebRTC video/audio, low-latency messaging, a Monaco editor, and automated test runners inside a single synchronized room.

Target Users

  • Hiring Teams & Technical Recruiters: Conducting live, reliable technical screening interviews with zero software download requirements for candidates.
  • Engineering Candidates & Peer Developers: Practicing complex Data Structures & Algorithms (DSA) solo or in realistic 1-on-1 mock peer interviews.

05. Complete End-to-End Request Lifecycles

Flow 1: DSA Question Selection & Session Creation

  1. User Trigger: On DashboardPage.jsx, user clicks "Create Session". CreateSessionModal opens.
  2. Selection: User filters by difficulty ("Medium") or searches "Two Sum". Problem data is selected from frontend/src/data/problems.js.
  3. Mutation Trigger: User clicks "Create Session". createSessionMutation.mutate(...) is dispatched via TanStack Query.
  4. Axios Interceptor: axiosInstance.interceptors.request intercepts outgoing request, calls await window.Clerk.session.getToken(), and assigns config.headers.Authorization = "Bearer <JWT>".
  5. Backend Ingestion: Express route POST /api/sessions invokes protectRoute middleware.
  6. Clerk Signature Verification: requireAuth() verifies RS256 token against Clerk JWKS public keys. Extracts req.auth().userId.
  7. JIT Database Provisioning: Middleware queries User.findOne({ clerkId }). If null, it queries Clerk Admin API (clerkClient.users.getUser), extracts email and profile data, executes an atomic upsert in MongoDB, and calls upsertStreamUser. Attaches document to req.user.
  8. Controller Execution (sessionController.js:createSession):
    • Generates unique callId (session_${Date.now()}_...).
    • Inserts session document into MongoDB (host: req.user._id, status: "active").
    • Calls Stream Video API: streamClient.video.call("default", callId).getOrCreate(...).
    • Calls Stream Chat API: chatClient.channel("messaging", callId, ...).create().
  9. Response & Client Transition: Backend returns HTTP 201 with session object. React Query triggers onSuccess, navigating user to /session/:id.

Flow 2: Remote Sandboxed Code Execution

  1. User Action: User writes JavaScript in Monaco Editor and clicks "Run Code".
  2. State Lock: Client sets isRunning = true to disable the Run button and prevent double execution.
  3. Direct Sandbox Call (frontend/src/lib/piston.js): Calls POST https://emkc.org/api/v2/piston/execute with language runtime version and code payload.
  4. Execution: Piston daemon spins up an ephemeral container, runs code, and returns stdout/stderr.
  5. Comparison (ProblemPage.jsx): Output string is normalized (trimming whitespace, brackets, commas) and evaluated against expectedOutput.
  6. Feedback: If passed, triggers canvas-confetti and success toast; displays formatted logs in OutputPanel.jsx.

08. Important Technical Concepts

Concept 1: Just-In-Time (JIT) Self-Healing User Provisioning

Hinglish Explanation:
Normal flow me jab user signup karta hai, Clerk ek webhook event (clerk/user.created) Inngest ko bhejta hai taaki user DB me save ho sake. Lekin local development me ya agar webhook network me drop ho gaya, toh MongoDB me user kabhi banta hi nahi. Result? Jab user session create karta hai, toh backend bolta hai "User not found". Humne iska solution nikala JIT Provisioning se: jaise hi user authenticated request bhejta hai aur DB me document nahi milta, middleware on-the-fly Clerk Admin API se profile fetch karke DB aur Stream me upsert kar deta hai. App kabhi fail nahi hoti!
Interview-Ready Answer:
"Instead of relying strictly on asynchronous webhooks which can fail or be dropped during network partitions, I implemented a Just-In-Time provisioning pattern in our Express authentication middleware. When a request carrying a cryptographically valid Clerk JWT arrives, the middleware checks MongoDB. If the user record is missing, it queries the Clerk Admin API, extracts user attributes, and performs an atomic upsert into MongoDB and Stream before attaching the record to the request object. This ensures our distributed auth state is completely self-healing."

Concept 2: Stateless Bearer Token Transport vs. Cross-Origin Cookies

Hinglish Explanation:
Frontend localhost:5173 par chal raha hai aur backend localhost:3000 par. Jab frontend alag port par hota hai, browsers cross-origin cookies ko block ya partition kar dete hain (especially Safari aur Chrome incognito me). Isliye humne Axios interceptor lagaya jo har request ke Authorization header me Bearer JWT daal deta hai. Ye 100% stateless aur foolproof hai.
Interview-Ready Answer:
"When developing distributed or decoupled SPAs, relying solely on ambient credentials like cookies introduces cross-origin partitioned cookie issues and strict SameSite blocking in modern privacy-focused browsers. I configured an Axios request interceptor that retrieves the active session JWT from Clerk's SDK and explicitly transmits it via the standard Authorization: Bearer <token> header. This guarantees stateless, reliable authentication across disparate ports and domain origins."

Concept 3: Selective Forwarding Unit (SFU) vs. P2P Mesh WebRTC

Hinglish Explanation:
Agar hum raw WebRTC use karein (Mesh architecture), toh har user ko doosre user ko direct video stream bhejna padta hai. 2 users me theek hai, lekin network fluctuating ho toh CPU aur bandwidth crash ho jata hai. Stream SDK SFU (Selective Forwarding Unit) use karta hai: video pehle ek central media server par jata hai aur wahan se optimize hoke receive hota hai.
Interview-Ready Answer:
"We utilized Stream's SDK because it operates on a Selective Forwarding Unit (SFU) architecture rather than a peer-to-peer mesh. In an SFU architecture, each client uploads their encrypted media stream once to a central edge server, which then routes it to other room participants. This minimizes client-side CPU usage and bandwidth consumption, handling varying bitrates dynamically."

09. Database Architecture & Models

The database layer uses MongoDB Atlas managed through Mongoose 8. It maintains two primary collections: users and sessions.

Collection Schemas

1. User Collection (backend/src/models/User.js)

const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, required: true, unique: true },
  profileImage: { type: String, default: "" },
  clerkId: { type: String, required: true, unique: true }
}, { timestamps: true });
  • Indexes: clerkId: 1 (unique, sparse), email: 1 (unique).
  • Critical Note: The index on clerkId is the primary query target during middleware verification. Without an index here, every protected API call would trigger a collection scan (O(N) time complexity).

2. Session Collection (backend/src/models/Session.js)

const sessionSchema = new mongoose.Schema({
  problem: { type: String, required: true },
  difficulty: { type: String, enum: ["easy", "medium", "hard"], required: true },
  host: { type: mongoose.Schema.Types.ObjectId, ref: "User", required: true },
  participant: { type: mongoose.Schema.Types.ObjectId, ref: "User", default: null },
  status: { type: String, enum: ["active", "completed"], default: "active" },
  callId: { type: String, default: "" }
}, { timestamps: true });
  • Relationships: host and participant store 12-byte BSON ObjectIds referencing documents in the User collection.
  • Population Query: Session.find({ status: "active" }).populate("host", "name profileImage email clerkId").populate("participant", "name profileImage email clerkId").sort({ createdAt: -1 }).limit(20);

Database Interview Questions & Answers

Q: Why MongoDB over PostgreSQL for this project?
"MongoDB provided schema flexibility during rapid prototyping of session attributes. However, because our sessions enforce relational foreign-key integrity between hosts and participants, a relational database like PostgreSQL with strict foreign keys and ACID cascade deletes would be the superior enterprise choice to prevent orphan session references."

11. Authentication, Authorization & Security

Authentication Implementation

  • Client-Side: Managed by Clerk React. On mount, Clerk loads session credentials into memory. The custom Axios interceptor in frontend/src/lib/axios.js attaches Authorization: Bearer <clerk_jwt> to every outgoing HTTP request.
  • Server-Side: Evaluated via @clerk/express in backend/src/middleware/protectRoute.js. requireAuth() cryptographically verifies the token using Clerk's public JWKS endpoint.

Authorization Implementation

  • Host Ownership Enforcement: In sessionController.js:endSession, the route verifies: if (session.host.toString() !== req.user._id.toString()) return res.status(403).json({ message: "Only the host can end the session" });
  • Self-Join Prevention: In joinSession, host cannot participate in their own room: if (session.host.toString() === userId.toString()) return res.status(400).json({ message: "Host cannot join their own session as participant" });

Security Vulnerabilities & Production Improvements

Vulnerability Current State Recommended Production Fix
Rate Limiting No rate limiting on POST /api/sessions. Implement express-rate-limit with Redis backing (max 5 sessions / hour / IP).
Input Validation Basic manual checks (!problem || !difficulty). Implement Zod schemas to validate string lengths, enums, and sanitize malicious payloads.
Compiler Exposure Direct client call to Piston API. Proxy compilation through backend microservice with token-bucket rate limiting.

13. Performance & Scalability Analysis

Current Performance Bottlenecks

  1. Client Polling (refetchInterval: 5000): In SessionPage.jsx, every connected user polls the database every 5 seconds. If 1,000 concurrent rooms are active, that creates 400 read requests per second to MongoDB.
    Solution: Replace polling with WebSocket event emissions or Server-Sent Events (SSE).
  2. Monaco Editor Bundle Footprint: Monaco is a heavy bundle (~2.4MB minified).
    Solution: Use dynamic imports (React.lazy()) so the Monaco chunk is only loaded when entering /problem/:id or /session/:id, keeping the landing page load under 150KB.
  3. Database Indexing: As sessions scale into millions of records, querying active sessions requires a compound index: sessionSchema.index({ status: 1, createdAt: -1 });

16. Brutal Weakness Analysis & Defenses

Weakness 1: Code in Monaco Editor is Not Synchronized in Real Time

  • The Issue: While video and chat are real-time, the code editor state is currently local to each user's browser. Keystrokes are not shared over WebSockets.
  • How to Answer in an Interview:
    "In this version, our real-time media layer (WebRTC video and chat) is fully synchronized via Stream, but the Monaco editor state is maintained in local component state. My immediate technical roadmap includes integrating Yjs with a WebSocket server or Stream's custom data channels. Yjs uses Conflict-free Replicated Data Types (CRDTs) to support seamless, collaborative Google Docs-style editing without keystroke collisions."

Weakness 2: Code Execution is Called Directly from Browser to Piston

  • The Issue: frontend/src/lib/piston.js calls the public Piston API directly.
  • How to Answer in an Interview:
    "We currently delegate compilation directly from the client to reduce server-hop latency during MVP testing. For an enterprise deployment, I would proxy this request through our Express backend, allowing us to enforce Redis-based rate limiting per user ID, sanitize input, and prevent third-party API key scraping."

18. Likely Interview Questions & Answers

Beginner Questions

Q: What is the purpose of the Axios interceptor in your frontend?
"The Axios request interceptor intercepts every outgoing HTTP request before it leaves the browser. It retrieves the latest session JWT from Clerk and sets the Authorization: Bearer <token> header automatically. This centralizes authentication logic and ensures no API call fails due to missing tokens."
Q: How do you prevent unauthorized users from accessing the dashboard?
"In App.jsx, we use Clerk's useUser() hook to verify isSignedIn. If the user is unauthenticated, React Router's <Navigate to='/' /> redirects them back to the landing page. On the backend, protectRoute.js validates the JWT signature; unauthenticated requests are rejected with HTTP 401 Unauthorized."

Intermediate Questions

Q: How does the backend enforce that only the host can end a session?
"In sessionController.js:endSession, the middleware attaches the authenticated user document to req.user. The controller queries the session document by ID, and executes: if (session.host.toString() !== req.user._id.toString()) return res.status(403).json({ message: 'Only the host can end the session' }); This guarantees that participants cannot terminate active interview rooms."
Q: How does your UI handle code execution test feedback?
"In ProblemPage.jsx, when Piston returns stdout, the client executes checkIfTestsPassed. It normalizes both the actual output and expected output by stripping whitespace, bracket padding, and trailing newlines. If they match, it triggers a confetti animation via canvas-confetti and renders a success toast; if they differ, it displays an error toast prompting the candidate to review their output."

Advanced / Tricky Questions

Q: Why did you choose TanStack Query over Redux Toolkit?
"Redux is built for synchronous client UI state, which requires writing dozens of boilerplate action creators, reducers, and thunks to manage async server data. TanStack Query is purpose-built for server state: it handles background caching, automated refetching intervals, window focus revalidation, and mutation states out of the box with zero boilerplate."

19. Deep-Dive Cross-Questioning Battlecards

Scenario 1: Interviewer asks "Why did you use Express 5 instead of Express 4?"
"Express 5 natively handles rejected promises in route handlers and middleware. In Express 4, an unhandled async error would cause the process to hang or crash unless explicitly wrapped in try/catch or an async handler helper. Express 5 also supports modern path-to-regexp syntax."
Scenario 2: Interviewer asks "What happens if MongoDB Atlas goes down during a live video call?"
"Because our video call and chat streams are routed directly through Stream's WebRTC infrastructure, an active call will continue functioning without interruption! However, session state operations—like ending the session or saving completed statuses to the database—would fail with a 500 error until database connectivity is restored."
Scenario 3: Interviewer asks "How would you prevent a candidate from cheating or running malicious code?"
"Because user code is executed on Piston's isolated sandbox, the host operating system is completely isolated. Piston sets strict cgroup boundaries: network access is disabled inside the container, execution runtime is capped at 5 seconds to prevent infinite loops, and memory is constrained to 256MB to prevent fork-bombs and memory overflow attacks."
